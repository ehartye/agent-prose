# Review workspace (batch review, side-by-side compare, "proof desk" redesign) - design

Status: decided by the owner on 2026-10-04 at the level of the three headline choices (see "Owner decisions"); the details below are the maintainer's resolution against the code at main `199c11f` (0.5.0 plus the brief, existing-line and strike-record milestones). The skin (W1), the compare view (W2) and batch review (W3) are built (#17, #18, #19), and the keyboard map shipped with W3. A later milestone, "W4: none of these" (added 2026-10-04, at the end of this document), is built as described there; the "W4: polish" row of the milestone table is otherwise not a separate milestone. Four milestones (W1 to W4), each shippable on its own. It edits the same page files as the strike milestones (M4 apply/undo, M5 voice bio) that are in flight on other branches, so every change below is written as an addition to the page as it stands, and the merge order is called out under "Milestones".

## Goal

The first live use of the reading page (a dialog pilot with many short lines) showed two costs: a lineup is a stack of cards, so comparing means scrolling, and a session is one set, so thirty lines means thirty links and thirty screens of back and forth. This spec gives the owner one page for a whole queue of sets, a lineup that puts the current line and the variants side by side with the differences marked, and a visual system made for reading short lines (the approved "proof desk" mock). Everything the owner records still goes through the existing CLI paths, so the logs, sealed predictions and the taste model do not change.

## Owner decisions (fixed)

1. **Batch review.** One session over many sets, opened with `prose reading open --sets a,b,c` or `--pending` (every set with a sealed prediction and no pick). A left rail lists each item (character and line; status waiting, picked or skipped), a progress count, keyboard next and previous, one page for the queue. Each pick is recorded per set through the existing `set pick`. `reading wait` returns picks as they arrive. Predictions stay sealed per set until its pick. A skipped item returns to the end of the queue; a batch may mix forms; at most 50 sets per session; the rail pages.
2. **Side-by-side compare** for the lineup: the current line and each variant as columns, lines aligned in rows, rows identical in every column folded into an expandable "N lines unchanged" row, at most four columns at once with a picker, measured numbers and Keep/Pass at the foot of each column, word-level markup (cut words struck on the current line, new words underlined on variants), two-up on a phone (current above one chosen variant, A/B/C pills). Duels keep their two columns at 900 px and up and are restyled.
3. **Visual redesign "proof desk"** exactly as the approved mock: the tokens, Courier Prime for lines and labels, Atkinson Hyperlegible for the UI (both OFL, vendored), the pencil circle (kept) and slash (passed) drawn once, reduced motion, visible focus, 44 px targets. The brief as a one-line summary that expands, the queue states, and "nothing sent until you press send" are in scope. The Draft view and the strike controls take the same skin.

## Principles (new, on top of the reading-page and line-review specs)

1. **Nothing about the data model of a verdict changes.** A pick is a `set pick` run by the server's CLI call, exactly as a ship is today. A batch adds a queue around ordinary sessions; it does not add a verdict kind.
2. **A session per set stays the unit of record.** The queue is an index and a staging area over child sessions, so every existing fold, transition rule, reveal and test keeps working unchanged.
3. **What the owner sees as "sent" must be true.** Choosing is a staged, reversible gesture; only "Send picks" runs `set pick`, and picks are irreversible, so sending is confirmed on screen.
4. **Colour and motion are never the only signal.** Every pencil mark has a text twin; every state has words.
5. **Draft text stays untrusted data**: `textContent` only, no inline style, the CSP stays no-external-requests. The diff markup is built from text runs, never from markup.

## 1. Visual system ("proof desk")

**Tokens** (`style.css`, replacing the current palette; light, then the dark equivalents from the mock under `prefers-color-scheme: dark`): `--paper #edefea`, `--sheet #fafbf8`, `--ink #17202a`, `--graphite #59636c`, `--rule #c9cfc8`, `--blue #1f4fd8` (kept pencil), `--red #c8341f` (struck pencil), `--mark #f3e58a`; dark `#12161b`, `#1a2027`, `#e9ece6`, `#9aa4ad`, `#2b333b`, `#86a7ff`, `#ff8f7a`, `#5b5217`. Role names move to the mock's (`--paper`, `--sheet`, `--ink`, ...); the old `--bg`, `--surface`, `--accent` and so on are removed in W1 in one pass. `html` is 17 px (18 px below 900 px), the mock's size; the reading page's current 18/19 px goes. Contrast is checked in a test (below), including `--graphite` and `--red` on `--sheet`, `--blue` on `--sheet`, ink on `--mark`, and the dark set.

**Type.** `--script: 'Courier Prime', 'Courier New', ui-monospace, monospace` for every line of draft text, speaker names, labels, column badges and the queue's names; `--ui: 'Atkinson Hyperlegible', system-ui, 'Segoe UI', sans-serif` for everything else. Courier Prime has a regular and a bold, Atkinson Hyperlegible a regular and a bold; nothing else is loaded, `font-display: swap` so text is never withheld, and the fallbacks are metric-close enough that the layout does not jump.

**Vendoring the fonts.** Both families are SIL Open Font License 1.1 (Courier Prime by Quote-Unquote Apps, Atkinson Hyperlegible by the Braille Institute of America). The OFL allows bundling and requires the licence text to travel with the files and the fonts not to be sold on their own; neither has a Reserved Font Name restriction that blocks subsetting under a different file name, but the safe course is to keep the original family names inside the files and only change the container.
- Files: `runtime/reading/fonts/courier-prime-400.woff2`, `-700.woff2`, `atkinson-400.woff2`, `-700.woff2`, plus `OFL-CourierPrime.txt`, `OFL-Atkinson.txt` and a `fonts/README.txt` (source URL, version, the subset command, the date). The `runtime` folder is already copied whole and fingerprinted by the managed runtime (`RUNTIME_FILES` includes `runtime`), so no copy list changes; a test pins that the managed copy contains the fonts.
- Size: the mock's four TTFs are 253 KB. Recommended: a Latin subset (U+0020-007E, U+00A0-00FF, U+2010-2027, U+2030-203A, U+20AC, U+2122) as woff2, about 15 to 30 KB each, produced once with `pyftsubset --flavor=woff2` (fonttools plus brotli) and committed, the command recorded in `fonts/README.txt`. That tool is not installed on this machine and needs a one-time install. W1 may ship the TTFs unchanged (253 KB, no tooling, `font/ttf`) and switch to woff2 later without touching code beyond the allow-list's four names and types; the milestone records which it chose. Time: woff2 adds about an hour to W1. Risk: a subset that drops a glyph the owner's dialog uses (accented names, a curly quote beyond the range) falls back to the system monospace for that glyph; the test renders every glyph of the test corpus against the subset's cmap. Maintainability: the subset command is a recorded one-liner; unsubsetted TTFs are simpler but quadruple the first-load bytes on a phone over Wi-Fi.
- **Server.** The static allow-list (`PAGES` in `server.ts`, a fixed table read once at `listen()`, never a path from the request) gains six entries keyed by exact request path: the four font files with `font/woff2` (or `font/ttf`) and the two licence files as `text/plain; charset=utf-8`, linked from a small "Fonts: SIL OFL 1.1" footer line. `loadPages()` reads them at start like the three page files and fails the same way if one is missing. They are served without the token, as the page files are (a `@font-face` fetch cannot carry the `x-prose-token` header). They get `Cache-Control: public, max-age=86400` instead of the blanket `no-store` (they are not secret and are named per version of the plugin); every other response keeps `no-store`. `/fonts/../server.json`, `/fonts/x`, `/fonts/` and a method other than GET are 404 or 405 (the table is exact-match).
- **CSP.** Today: `default-src 'self'; style-src 'self'; script-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. There is no `font-src`, so fonts already fall back to `default-src 'self'`, and same-origin font files are allowed with no change. W1 still adds an explicit `font-src 'self'` (so a later tightening of `default-src` cannot silently break the fonts, and the test can pin that fonts are same-origin). Nothing else changes: no `data:` (fonts and the marks are not data URIs), no `unsafe-inline` (the SVG marks are created with `createElementNS` and animated by a class and a CSS keyframe, never a `style` attribute; `pathLength="1"` is an attribute, not style), no `img-src`, no external host. A test pins the whole string and that it has no `http` and no `unsafe`. The static page test's "no third-party URL" regex still scans `app.js`, `index.html` and `style.css`; the licence `.txt` files are excluded from that scan (they quote URLs) and the font binaries are never read as text.
- **`tests/reading-page.test.ts` changes** (named so nobody is surprised): the "has the three page files" assertion becomes "the page files plus `fonts/`", the `readdirSync` loop in the banned-API test skips directories and non-text files, and `index.html` may now reference `/fonts/` only through CSS (the html test that pins `['/app.js', '/style.css']` stays true; `@font-face` lives in `style.css`).

**The marks.** A pencil circle (kept, `--blue`) and a slash (passed, `--red`), exactly the mock's two SVG paths (`pathLength="1"`, `stroke-dasharray: 1`), created by one `h()`-style helper with `createElementNS`. They draw once, in 0.42 s, when a column's state changes to kept or passed (a CSS class on the column, not a timer), and are fully drawn with no animation when the page loads on a state that is already set. With `prefers-reduced-motion: reduce` they appear drawn at once (the mock's rule, kept), and no other animation exists. Marks are decorative (`aria-hidden="true"`); the state is also a word (see "Accessibility").

**Focus and targets.** `:focus-visible` is the mock's 3 px `--blue` outline with 2 px offset, on every control including rail items, pills, fold buttons and cells; `outline` is never removed. Every control is at least 44 by 44 CSS px (including the fold button and rail items, which the mock gets right and the fold does not). The sticky bottom dock respects `env(safe-area-inset-bottom)`.

**Layout.** One shell for every screen: at 900 px and up a `desk` grid of a 17 rem rail and the work area; below 900 px a single column with the rail as a horizontal chip row (the mock). A single-set session has no rail (the shell collapses to the work area, centred to 72 rem); the title row is `who - line` with the context beside it, replacing the current `h1` and subtitle. The brief is a `<details>` closed by default with a one-line summary (the character's first sentence, falling back to the context) and "Not confirmed with you yet" as a visible chip in the summary when unconfirmed; opening it shows Character and Context in two columns. The bottom dock is one fixed region holding, from top, the pending-strike bar (when present, as today) and the action row (tally, "Next unchosen", "Send picks" in a batch; the existing action buttons otherwise). Cards on the duel and refine screens become sheets (hairline border, `--sheet`), the duel's two columns at 900 px keep their structure and their bottom bar, and the Draft view's lines and the strike picker take the same rule lines, buttons and chips.

**Existing behaviour that changes visibly** (so the maintainer and owner are not surprised): the whole palette and both typefaces; text sizes (17/18 px); the reading column (70ch max-width) becomes full-width sheets; the lineup is a grid, not a stack of cards (at 900 px and up; below it, the two-up layout); the brief starts folded; the title and subtitle move into the title row; buttons are 4 px-radius rule-line buttons; the strike bar and the notice move into the dock and under the title row; read-aloud controls move into each column head and the rate slider into the foot. What does not change: the stage flow (lineup, duel, refine, wait, shipped), the confirmations, the sealed reveal screen's content, the poll cadence, the "What changed?" behaviour, the note, play and strike behaviours.

## 2. Side-by-side compare (lineup)

**Where it applies.** The lineup stage of a single-set session (every round) and of every batch item. Duel, refine, waiting and reveal keep their screens (restyled). A set whose variants cannot be compared (`changed` after sealing, or a draft over 1,500 units) falls back to the card stack for that screen, with the same skin.

**Columns.** `Current` (when the set has an `original`) then variants in display order (the existing `displayPlan` order and letters A, B, C, so a variant keeps its letter). In a round after the first, the pinned champion is the Current column's neighbour and tagged "Your pick from last round". The picker is a row of pills, one per variant, `aria-pressed`, labelled "Show in the comparison"; it is shown only when the set has more variants than fit (more than 3 with a Current column, more than 4 without); the first columns in display order are the default; at the limit, choosing a further variant swaps out the least-recently chosen one, and the pills say which are visible in text ("A B C shown"). Kept and passed marks are by variant, not by column, so hiding a variant never loses its mark. On a phone the pills are the A/B/C chooser and exactly one is pressed.

**Rows.** One row per unit of the base text, in order, with the unit number in a left gutter (mock). A row is `same` when every visible column has the same normalised text and speaker; a run of `same` rows is one fold: a button "N lines unchanged" plus up to three of the speakers and numbers ("TALLY-4, line 3 - TALLY-4, line 5"), 44 px high, `aria-expanded`, expanding in place (a `same` run shown plain, in the Current style). "Expand all" and "Fold all" are in the title row. A row of the draft is never hidden without this visible, expandable bar. Because folds depend on the visible columns, they are computed in the page from the per-variant data below, so the picker and the phone chooser re-fold without a request.

**Alignment (server, `src/reading/compare.ts`, pure and unit-tested).** Inputs are the base's units and each variant's units, from `blockUnits`/`layoutOf` as the page already uses them (so a cell is `{ unit, speaker?, text }`, the speaker read from the block, not parsed back out of the `Name: ` prefix, which a script action line could fake). The row space is the base units. For each variant independently: trim the common prefix and suffix by exact normalised equality (speaker plus text, whitespace collapsed, case and punctuation kept), then align the middle by a longest-common-subsequence over the same keys, bounded to 400 by 400 (above that, the middle is one gap). Between matched anchors a **gap** has base units and variant units. Equal counts pair by position (a rewrite of line i). Unequal counts are paired by a small dynamic programme over `similarity()` from `src/owner/similarity.ts` (the existing blend of word and phrase overlap), pairing only above 0.2 and preserving order, bounded to 20 by 20 (above that, by position); what is left unpaired is an **added** unit (a variant line with no base line) or a **removed** one (a base line the variant lacks). Rows are keyed by base unit index; added units go into insertion slots after the preceding base row, row j of the slot holding each variant's j-th insertion, so variants that add different counts share rows and leave the others' cells empty. An empty Current cell on an added row reads "No line here" and an empty variant cell on a removed row reads "Line removed", both muted text with the same weight as a line (a state in words, not a blank). A variant that adds or removes lines therefore appears as extra or gapped rows, never as a shift of every later row.

**Word diff (server, same module).** For each paired, changed cell the module tokenises both texts as `\S+\s*` runs, compares trimmed tokens exactly, and runs a longest-common-subsequence over them (at most 120 tokens each; beyond that the cell is one cut run plus one new run), returning `ops`: `[['=', 'Does the feeling '], ['-', 'or are you billing it by the hour?'], ['+', '...']]`. The page renders runs as text nodes inside `<del>` and `<ins>`; it computes nothing else. Computed on the server for three reasons: the TypeScript similarity and `words` code is there and has no page build to reach it; the tests are plain vitest; and one implementation cannot drift between the page and the CLI's `wait` output. Cost: payload only for changed rows (same rows carry one `cur` cell and no per-variant cells).
- **Variant cells** render `=` runs plain and `+` runs as new words (`ins`, the mark band; underline in forced-colours mode; preceded by a screen-reader "added:" and followed by "end added").
- **The Current cell** is struck per word, derived in the page from the visible variants' `-` runs: a word cut in every visible variant is struck solid; a word cut in some but not all is struck dashed with the hidden text "cut in A, C"; a word no visible variant cut is plain. On a phone (one variant) that is exactly that variant's cuts. This is the one place the owner decision ("cut words struck on the current line") needed a rule: with several variants, a union would strike everything and an intersection would hide a cut that only one variant makes; solid-or-dashed shows both.
- Rows with no `original`: no Current cell, so no strikes; new words are still underlined against the base, which is then only the alignment reference.

**Cache and cost.** `compare` is built per (set, variant hashes, base hash) and kept in the server's stat-keyed memo like `textCache`, so a poll that finds nothing changed does no alignment. Worst case per variant: LCS bounded 400 by 400 (160,000 steps), the gap DPs 20 by 20, the token LCS 120 by 120 per changed cell; for six variants of a 300-unit draft that is well under 50 ms once and zero afterwards.

**Payload.** `SessionPayload` gains `compare: null | { base: Cell[] ... }` in this shape (lineup stage only; `null` otherwise or when over the limits):

```ts
type Op = ['=' | '+' | '-', string];
interface Cell { unit: number; speaker?: string; text: string; ops?: Op[]; struck?: true }   // unit: index in that variant's units (a note's target)
interface Row { base: number | null; cur: Cell | null; cells?: Record<string, Cell | null>; same?: true }  // cells keyed by candidate index; omitted when same
compare: { hasCurrent: boolean; rows: Row[]; truncated?: true }                                // at most 600 rows; `same` rows past 300 carry no text
```

Each row of a duplicated draft is sent once. `candidates[].units` stays in the payload for the other screens, read-aloud and timing (a lineup of whole-draft copies therefore sends text twice; the cap and the memo bound it, and a later change can drop `units` on compare screens). The page's `signature()` gains `compare` presence only through the existing stage, round and event count, since compare derives from files the hashes already freeze.

**Foot of each column** (replacing the card's timing block and buttons): the words and read time against the target (`timingText`, the existing measured text, whole variant) and "N of M words new" from the ops; the existing "What changed?" toggle (peek, direction, angle, note); Keep and Pass buttons whose labels become "Kept" and "Passed" when set (the existing wording); in a batch the kept column also carries "Your pick". The Current column's foot is its own word count and read time. The read-aloud Play/Pause sit in the column head and highlight the active unit's row (cells carry `data-unit`), using the existing speech code unchanged. Tap-to-note on a variant cell (the existing unit note) works in single-set sessions; in a batch it is off (see below).

**A variant that changed after sealing** keeps today's rule: its column shows "This draft changed after it was sealed; it can't be chosen" and no Keep.

## 3. Batch review

### Batch items are quick picks

A batch item runs one step: choose a variant (or none), with optional Pass marks. It has no duel, no refine round and no notes. That is a visible loss against a single-set session (duels feed the taste model with `duel` rows; refine is how the agent hears "more like this"), so it is stated plainly: a batch yields pick rows and engagement events, not duel rows. Escape hatch: every item has "Open as its own session" (a link to `/s/<child session id>`), which is the full single-set flow for that item; if the owner ships there, the queue sees the child shipped and shows the item as sent. Recommended default; the alternative (duels and refine rounds inside a batch) is listed under "Decisions for the owner".

### Data model: a queue over child sessions

A **queue** is a new, small record beside the sessions; **each item is an ordinary `prose/session@1` session** created by the existing `openSession` (its own id, `session.json`, `events.jsonl`, hashes frozen from that set's sealed prediction, reveal after its pick). Nothing about `SessionRow`, `foldSession`, `checkTransition`, `reading round` or the single-set URL changes. This is the main design choice; the alternative, one session holding many sets, would have made `foldSession` (one stage, one champion, one lineup) carry N parallel state machines.

| Piece | Change |
|---|---|
| `SessionSchema` | one new optional field `queue: z.string()` (the queue id), written only for child sessions. It is a `strictObject`, so an older runtime cannot read a child session (the same one-way door as the set fields; the plugin updates as a unit). Absent for every session that exists today. |
| `src/owner/paths.ts` | `queuesDir(project)`, `queueDir(project, id)` = `.agent-prose/queues/<id>/`, ids from `newId('queue')` (`queue-20261004-1830-ab12`, matches `ID_RE`, so `validId` and the locks apply). `initProject` adds `queues/` to the `.gitignore` it writes for new projects (existing ones keep theirs; the README says to ignore it). |
| `src/reading/queue.ts` (new) | `queue.json`: `{ schema: 'prose/queue@1', id, project, createdAt, prompt, items: [{ n, setId, sessionId, form, who, where, predicted }] }`, written once, atomically, last (after the child sessions exist). `n` is 1 to 50 and never changes. `who` and `where` are frozen labels: `who` is the first original line's speaker, else the set id; `where` is `<draft file name>, line <ref>` from the original's first ref, else the set's form. `events.jsonl`: append-only rows `{ at, seq, type, eventId? }` of the types below, a zod union, a torn or unknown line skipped and counted (the session log's rules), appended under the existing directory lock (`withDirLockAsync` in the server, `withDirLock` in the CLI). A pure `foldQueue(queue, events, childStates)`; no I/O in the fold. |
| Queue event types | `choose { item, variant: number \| null, passes: number[] }` (the staged choice for item `n`: the session candidate index kept, and the ones passed; `variant: null` clears it), `skip { item }`, `send { sendId, items: number[] }` (an audit marker written when a send starts), `finish`, `close`. There is no `sent` event: an item is **sent** when its child session is `shipped`, read from the child (authoritative: it also covers an item shipped from its own session link). |
| Caps | 4,000 queue events (`choose` and `skip` refused with 429 "queue is full" beyond; `send`, `finish`, `close` always accepted, the session rule); `passes` at most 6; an `item` is an integer 1 to 50. |

**The rail's order** is derived: item order 1..N, each `skip` moving that item to the end (a stable queue), so an item skipped twice is last twice. **Status** per item, from the fold and the child: `sent` (child shipped), `picked` (a staged choice with a variant, not sent), `skipped` (its latest staged action is a skip and it has no choice), `blocked` (a send attempt failed for it; with the message), `ended` (child abandoned), else `waiting`. The owner's three statuses map as: waiting; picked (with the sub-state "sent" or "not sent"); skipped. A choice made after a skip clears `skipped`; a skip after a choice clears the choice (the item returns to the end, unchosen).

### Opening a batch

`prose reading open --sets a,b,c` or `--pending` (exactly one of `--set`, `--sets`, `--pending`, else E_USAGE). The existing flags apply: `--local`, `--no-predict`, `--prompt`, `--dir`. Additions: `--limit <n>` (for `--pending`, at most 50, default 50).
- **`--sets`**: a comma list, order kept, duplicates E_USAGE, at most 50 (else E_USAGE with "split it into batches of 50"). Every set is checked as `open --set` checks it today (`checkSet` for two surviving variants, the sealed prediction rules, `predictionProblem` for a tampered seal). Validation is **all-or-nothing**: any failure lists every failing set with its reason (`E_USAGE`, or `E_PREDICTION_REQUIRED` when the only problem is a missing seal, with the same hint) and nothing is created. `--no-predict` lets sets with no seal in (recorded per child as `predicted: false`); sets that have a seal keep it, as in a single open.
- **`--pending`**: every set in the project with a sealed, intact prediction, no `picked`, passing `checkSet`, and no open (not shipped, not abandoned) session for it (or for any later round's set). Oldest first by `createdAt`, at most `--limit`. Sets that fail a condition other than "no prediction" are skipped with a reason in the output rather than failing the batch (the owner wants "everything ready"). Zero sets is E_USAGE ("nothing is waiting for a pick") with a hint to predict first.
- **Creation order**: validate all, ensure the server and register the project (as today), create the child sessions (`openSession` with `queue` set, the queue's `prompt` copied to each), write `queue.json` last. On any failure the children created so far are removed (best effort) so no orphan sessions remain. Mixed forms are allowed: each child carries its own form, wpm and target.
- **Output** (`id` and `url` keep their meaning, so a caller that reads them keeps working): `{ id: <queue id>, kind: 'queue', url, ipUrls, items: [{ n, set, session, who, where, predicted }], skipped: [{ set, reason }], remaining: <pending sets beyond the limit>, wait: 'prose reading wait --id <queue id>', predicted: <all predicted>, notice }`. The URL is `/q/<queue id>?t=<token>`; `/q/<id>` joins `/` and `/s/<id>` in the server's page route (same `index.html`).

### Routes (`SERVER_API`: +1 over whatever main holds when W3 merges)

The page addresses a set inside a queue by `n`, never by a session id or a path. A queue route resolves `n` to a child session through `queue.json` (validated ids, the project from the registered roots) and then runs the **same handler** as the session route.

| Route | Does |
|---|---|
| `GET /api/queue/<qid>` | the rail: `{ queue: { id, prompt, total, counts: { waiting, picked, sent, skipped, blocked, ended }, stage: 'open' \| 'finished' \| 'closed' \| 'done', cursor }, items: [{ n, who, where, form, status, picked: label \| null, message? }], order: [n...], current: n }`, about 300 bytes per item (15 KB at 50). Built from the per-child `rowCache` (stat-keyed on `session.json` and `events.jsonl`) plus the queue log's stat, so a poll that finds nothing changed reads nothing. |
| `GET /api/queue/<qid>/item/<n>` | the existing `SessionPayload` of the child (with `compare`, `brief`, `original`, `draft`), plus `queue: { n, status, choice: { variant, passes } }`. |
| `GET\|POST /api/queue/<qid>/item/<n>/<rest>` | `rest` is one of `event`, `reveal`, `strike`, `strike/clear`, `strike/preview`, and M4's `strike/apply` and `strike/undo` when present: the session handler for that child, so the Draft view and strikes work in a batch with no new code. `event` is further restricted: only `play` and `peek` are accepted; `lineup`, `duel`, `refine`, `ship`, `abandon` and `round` are refused with 403, because a pick may only go through `send`. |
| `POST /api/queue/<qid>/choose` | `{ item, variant \| null, passes, eventId }` (strict zod); refused for a sent or ended item and for a variant that changed after sealing or is not in the child's `shown`. |
| `POST /api/queue/<qid>/skip` | `{ item, eventId }`. |
| `POST /api/queue/<qid>/send` | `{ sendId, eventId }`; see below. |
| `POST /api/queue/<qid>/finish` | `{ eventId }`. |

All POSTs keep the existing guards: token, the `Host` check on a local bind, the `Origin` check, the 64 KB cap (these bodies are under 200 bytes), the per-queue `serial()` queue, event-id idempotence, and the error pass-through. Notes are not offered in a batch (the `note` event needs a refine to be useful), so the `event` route accepts `play` and `peek` only there; peeks still record that the owner opened "What changed?".

### Send picks (decided: staged, then one confirmed send)

Choosing Keep is staged in the queue log, durable across reloads and devices, and reversible (Keep again to clear, or choose another). **Send picks** opens an inline review (focus moves to its heading; Escape or "Not yet" closes it): one line per chosen, unsent item ("TALLY-4, line 4: B - Feelings now? Fine...", the first 60 characters, as text), the sentence "Picks cannot be changed once sent," and the buttons "Send 4 picks" and "Not yet". Confirming runs, for each chosen unsent item in rail order, one at a time under the queue's `serial()`:
1. an `event` of type `lineup` on the child with `kept: [variant]`, `duds: <passes>`, `order: <the child's shown order>` (event id `<sendId>-<n>-l`); this moves the child to the refine stage by the existing fold (one kept means no pair to duel);
2. an `event` of type `ship` on the child with `champion: variant` (event id `<sendId>-<n>-s`), through the existing `applyEvent`: the CLI `prose set pick <set> --pick <v>` (`--no-predict` when no seal) runs first, the reveal is written, and only then is the ship appended. Nothing about pick rows, weights, the ledger, the sealed prediction or the model's prediction changes; the Keep and Pass marks are stored as the ordinary `lineup` engagement event.
3. A child already shipped for that variant (a retry, or an external ship) counts as sent; a child shipped for another variant is `blocked` with "this set was picked elsewhere".
The response is per item: `{ ok, results: [{ n, status: 'sent' | 'blocked', message? }], state }`. A failure on one item (a changed variant file: E_CONFLICT; a set picked in the CLI meanwhile: E_CONFLICT) marks only that item `blocked`, shows its CLI message and hint in the item and the rail, and lets the rest proceed; a blocked item can be re-chosen and sent again. A whole-request retry with the same `sendId` is harmless (every step is idempotent by event id and by the child's state). "Send picks" is enabled when at least one item is chosen and unsent. The copy is true in every state (see tally below), and the picks the agent sees are exactly the picks the owner confirmed.

**Finish.** "Finish" ends the review: if chosen picks are unsent it asks "Send them first?" (Send and finish, Finish without them, Back). `finish` abandons every child that is not shipped (the `abandon` event, per child) and records the queue event; unsent staged choices are dropped, the sets stay unpicked with their seals intact, so a later `reading open --pending` offers them again. After `finish` or `close` the page shows a summary ("3 sent, 2 not chosen") and every control is disabled.

### Tally and queue copy

"{chosen} of {total} chosen" always, then: nothing sent and something chosen: "nothing sent until you press send"; some sent and some staged: "{sent} sent, {staged} not sent yet"; all chosen sent: "{sent} sent". With nothing chosen the tally is the count alone. Skipped items are counted in the rail summary line ("2 skipped, back at the end"), not in "chosen". "Next unchosen" goes to the next item in rail order that is waiting or skipped (wrapping), and says so in its label when none remain ("All chosen"). The rail shows each item as `who`, `where` and a visible status word ("Waiting", "Picked B, not sent", "Sent B", "Skipped", "Blocked: <reason>", "Closed") beside the pencil state.

### `reading wait` and `reading status` for a queue

`--id` takes a session id or a queue id (a queue id is looked up first; ids cannot collide, the prefixes differ, and `readSession` failing leaves a single clear error naming both). Single-set sessions behave exactly as today; nothing below applies to them.

- **`prose reading wait --id <qid> [--since <n>] [--timeout <s>] [--settle <s>]`.** A pick is **delivered** once, by its rank in ship order (the child's ship `at`, ties by item number). `--since` is the number of picks already delivered (default 0), so the call is stateless and a lost reply is recovered by asking again with the old cursor. It returns the picks delivered after `--since` once there is at least one and no further pick has shipped for `--settle` seconds (default 1.5, so one Send click's picks come back together), or immediately on `finish`, `close` or a completed queue. Output: `{ event: 'picks', picks: [{ item, set, session, who, where, form, variant, label, reveal }], cursor, counts, done: false, next }` where `cursor` is the number to pass next and `reveal` is the child's reveal (the sealed prediction and whether it matched, now unsealed because that item has been picked; unpicked items stay sealed and are never in the output). When the queue ends: `{ event: 'done', reason: 'all-picked' \| 'finished' \| 'closed', picks: [...since], unpicked: [{ item, set }], cursor, counts, next }`. On timeout, `{ timeout: true, cursor, counts, next }` like today. **Done condition**: every item is sent, or the owner pressed Finish, or the agent ran `reading close`. A skipped or waiting item is never "done" by itself, because a skip returns it to the queue.
- **`prose reading status --id <qid>`**: `{ id, kind: 'queue', stage, total, counts, cursor, items: [{ n, set, session, who, where, status, picked, variant, label, reveal }], order }` (the reveal and `picked` only for sent items; staged choices are **not** reported, since an unsent choice is not a pick and the owner may still change it). Nothing sealed is read for an unpicked item.
- **`reading list`** gains `queues: [{ id, stage, total, sent, createdAt }]` and no longer lists child sessions as sessions of their own (each shows under its queue; the child row, if asked for by id, carries `queue`). **`reading close --id <qid>`** abandons every unshipped child, writes `close`, and leaves picks already sent untouched. `reading round` on a child is E_USAGE ("a batch item has no rounds; open the set as its own session"); `wait --id <child id>` still works.
- **Backwards compatibility.** `open --set`, the `/s/<id>` URL, `wait`/`round`/`status`/`list`/`close` on a session id, the event shapes and the single-set page flow are unchanged. JSON outputs only gain fields. A new page against an old server or the reverse is handled by `SERVER_API`: a running server of another level is replaced and keeps its token and projects.

## 4. Keyboard and the rest of the interaction

Shortcuts are plain keys, active only on the desk (not inside a text field, select or textarea, and never with Ctrl, Alt or Meta held except Ctrl/Cmd+Enter). They can be turned off from the "Keys" button in the dock (stored in `localStorage` with a try/catch, default on), which also satisfies the WCAG rule for single-character shortcuts; every action also has a visible control. `?` opens the same map as an inline panel.

| Key | Does |
|---|---|
| `j` / `k` | next / previous item in rail order (batch); next / previous page of the picker on a phone chooser (single set) |
| `a` to `f` | Keep that variant (a batch: choose it; a single set: toggle keep); on a phone also shows it |
| `Shift` + `a` to `f` | toggle Pass on that variant |
| `u` | clear this item's choice and passes |
| `s` | skip this item (batch) |
| `n` | next unchosen |
| `e` | expand or fold all unchanged rows |
| `b` | open or close the brief |
| `p` | play or pause the focused column (when the browser can speak) |
| `Ctrl/Cmd+Enter` | open the Send review (batch) or Continue (single set); in the review it confirms |
| `Escape` | close a panel (review, keys, picker) and return focus to the control that opened it |
| `?` | show the map |

After every move focus goes to the item's title row (a heading with `tabindex="-1"`) and a polite live region says "Item 3 of 5: TALLY-4, line 4, waiting", so a keyboard or screen-reader user is not left on a removed node. Arrow keys are not bound (they scroll). Item selection also changes `location.hash` to `#<n>` with `replaceState`, so a reload lands on the same item (the token is already in session storage; the hash is never sent to the server).

## 5. Accessibility

- **Text twins for every mark.** Rail: a status word beside the circle or slash. Column head: "Your pick" / "Passed" / nothing, as visible text. Buttons: "Keep" and "Kept", "Pass" and "Passed", with `aria-pressed`. Diff: `ins` and `del` (semantic elements), a struck word also has the visible line-through (not only red) and the hidden "cut" text, a new word has the hidden "added" text; the dashed (some-variants) strike has "cut in A, C". The pencil circle and slash are `aria-hidden`.
- **Structure.** The rail is `<nav aria-label="Review queue"><ol>`, each item a button with `aria-current="true"` on the open one and a label that reads the whole state ("TALLY-4, Wake-up scene line 4, picked B, not sent, item 1 of 5"). The grid is a real structure: rows are `role="row"` inside a `role="table"`-like grid made of one element per cell with `role="rowheader"` for the line number, `columnheader` for each column head, so a screen reader can read down a column or across a row. The title row is the heading. The send review and keys panel are `role="region"` with a labelled heading, not modal dialogs (no focus trap to escape; Escape closes). The dock tally is `role="status"`.
- **Colour.** Every text colour pair is tested for 4.5:1 and every control boundary for 3:1 in both schemes; forced-colours mode maps rules to `CanvasText` and underlines new words; neither the picked/passed nor the added/cut distinction relies on hue.
- **Motion.** The two marks draw once; reduced motion draws them at once; there is no other motion, no auto-advancing and no timed state. Auto-refresh re-renders only when the signature changes, and a re-render keeps focus on the same control (found by a stable `data-key`).
- **Targets and zoom.** 44 px minimum; the layout reflows with no horizontal scroll at 320 px and at 200% zoom (the grid becomes the phone layout below 900 px CSS width).

## 6. Performance and security

**50 sets.** Open creates 50 session directories and one queue file: well under a second. The rail payload is about 15 KB. The page polls the rail every 8 s (2 s while a send is in flight) and the current item's payload at the same cadence as today; the other 49 items are not polled, and the next item is fetched once, in idle time, so "next" is instant. Server cost per poll is stats against the existing caches; a send is at most 50 children times two events plus one CLI `set pick` each (about 150 ms per process start, so a full send of 50 is on the order of 8 seconds, shown as "Sending 7 of 50" in the dock, which is a human-paced action). `--pending` scans sets and sessions once.

**Token and authorization.** Unchanged and stated honestly: one token per server; any holder can read every registered project's drafts and run every route, whether or not it goes through a queue. The queue does not add a boundary and does not weaken one: queue routes resolve `n` through `queue.json` (never a client-supplied session id or path) so a queue page can only name its own children, and refusing `lineup`, `ship` and the rest on the queue route keeps a page from skipping the confirmed send. That is integrity, not secrecy: a holder who wants to ship can call `/api/session/<child>/event` directly, exactly as today. What grows is the blast radius of one click (50 picks, not 1) and the link's reach (a queue link names 50 sets), so the notice printed on every `open` and `serve` also says the link can record picks (today it says drafts can be read and lines marked struck; M4 will add removal; W3 appends the picks sentence after M4's text lands, to avoid editing the same string twice). Predictions stay sealed per set: the reveal route answers 404 until that child has shipped, the rail and queue payload never contain a prediction, and `wait` and `status` unseal only picked items.

**Other.** Queue bodies are strict zod objects with every number bounded; ids go through `validId`; `n` is an integer 1 to 50; the `sendId` and event ids use `EVENT_ID_RE`; the fonts table is exact-match; errors keep the path scrubbing. The queue log is capped like the session log, and a torn line is skipped and counted. A queue left open is harmless on disk (small files; ignore `queues/`, like `sessions/`).

## 10. Decisions for the owner

1. **Batch items are quick picks (recommended) or full flows.** Quick picks: about 4 days for W3, low risk, no change to the session fold, a batch gives pick rows only and the escape hatch is the item's own session. Full flows (lineup, duels and refine inside a batch): about 6 to 8 days, high risk (each item then needs its own wait, round and pending-refine state in `wait` and a queue-level answer to "who is the agent waiting on"), more taste data per item, and a much heavier `wait` protocol. Best practice and maintainability both favour the first; take the second only if duels in a batch matter to the taste model.
2. **Keep in a batch is a radio** (the mock) and in a single-set lineup is multi (today's). The two share a label; the alternative is to call the batch control "Choose". Cost of the shared label: a user learns one word with two behaviours, softened by the "Your pick" text and the tally. Cost of two labels: the mock changes in the one place it was approved.
3. **Fonts: ship woff2 subsets (recommended) or the TTFs as they are.** woff2 is about one hour more in W1, needs a one-time `fonttools` install, and cuts the first load from about 253 KB to under 100 KB; TTFs ship today with no tooling and can be swapped later.
4. **Direction scores in the foot** ("drier +0.14") are dropped here (they are not in the data and the page hides directions by default). Say so if you want a per-variant feature delta built.
5. **Browser tests in CI.** Recommended on both runners (Chrome is preinstalled, so no download), about 1 to 2 minutes extra per OS; the alternative is a local gate recorded in each PR, which is faster to ship and easier to forget.

## 11. Out of scope

Duels and refine rounds inside a batch; notes inside a batch; reordering the queue by hand; a batch across projects; changing a pick after Send; per-item undo of a sent pick; direction scores in the foot; a manual theme switch; a view-only token or per-set authorization; sentence-level strikes; dropping `units` from compare payloads (a later size optimisation); offline use; accounts or HTTPS (the threat model is still the home network and a link token).

## 12. Risks

- **Two behaviours for Keep.** Mitigated by text states and the tally; owner decision 2 above.
- **Alignment is heuristic.** A rewritten line paired to the wrong base line shows as a changed row with a big diff, never as lost text, and every unit appears in exactly one row per variant (tested as an invariant). The fall-back bounds make worst cases show more change, not less.
- **The queue and a child can disagree** (a child shipped from its own link, abandoned by `reading close --id <child>`). The child is authoritative for "sent" and "ended"; the queue's own log only holds staging, skips, finish and close, so there is nothing to reconcile.
- **A send is not atomic across items.** It is per item and idempotent; the worst case is some items sent and some `blocked` with a reason, which the response and the rail show.
- **Page weight.** Whole-draft variants make the lineup payload carry text twice until `units` is dropped on compare screens; capped by the 1,500-unit and 600-row limits and the fall-back.
- **Merge conflicts** with M4 in `app.js`, `style.css` and the server's route table. Mitigated by landing W1 after M4 and by writing the queue routes as a wrapper over the session handlers instead of editing them.
- **Font subset gaps** fall back to the system monospace for a missing glyph; the corpus test is the guard.
- **Character-key shortcuts** can collide with assistive technology; mitigated by the off switch, field and modifier exclusions, and visible controls for everything.

## W4: none of these

Owner request (2026-10-04): "need a way to give feedback when none of the options are good". Until now the only outcomes of a set were a pick (or a ship) and, for a single line, a strike (a record that the line should go). This milestone adds the outcome "none of these": the owner rejects every variant and says why. It is built as written here; where the code forced a change from the design as first decided, it says so (see "Deviations").

### What the owner sees

- **A "None of these" button** on every lineup: in the action bar beside Continue in a single-set session (compare view and the card-stack fallback alike), and in the item bar of every batch item (beside Skip and Clear choice). It is not offered on the duel or refine screens: by then the owner has already kept something.
- **A panel** (a modal dialog: the proof desk skin, 44 px targets, focus moves to its heading, Tab stays inside it, Escape or Cancel closes it and returns the focus to the button; the page behind it is `inert`). It asks, in order: **Which came closest?** (a radio of the shown drafts A, B, C... plus "None came close", preselected); **What is wrong?** (reason chips, any number, each with a text state, "chosen"): Wrong direction, Doesn't sound like them, Too similar to each other, Misses the point of the scene, Too long, Too short, The premise is wrong, Other; and a note (a textarea with an "n / 1000" counter). **Send back** needs at least one reason or a note and a note within 1000 characters after trimming; the reason it is disabled is written under the note. Choosing "The premise is wrong" shows the hint "If the line itself should go, strike it in the Draft view" with a link that closes the panel and switches to the Draft view (what was typed is kept for when the panel is opened again on the same item). The panel is built once and updated in place, so a poll that re-renders the page never takes the owner's typing or focus. An error from the server stays inside the panel.
- **After sending back (single set):** the session ends. The page shows what the owner said (closest draft, reasons, note) and the reveal, headed **No pick to compare**: the agent's sealed guess is shown and plainly not scored.
- **A set made with `set new --redo`** shows "Sent back last time: <reasons>, <note>" above its variants (display only; the closest draft is not shown, because the new set's letters have nothing to do with the old set's).

### Recording

- **CLI**: `prose set none <id> [--reason a,b] [--note "..."] [--closest <n>]`. Every write goes through it; the reading server only ever calls it. `src/owner/feedback.ts` is the single definition of the vocabulary and the validation: reasons are a fixed enum (an unknown one is E_USAGE, a repeat is dropped), the note is trimmed, line endings folded, control characters refused, at most 1000 characters after trimming (E_USAGE), plain text only (never executed or rendered as markup by the CLI; the page only ever sets it as text), and at least one reason or a note is required. `--closest` must be one of the variants the owner was shown (the sealed prediction's frozen list, else what the set check keeps). The server validates the same way before it calls the CLI, and the session event schema and the queue event schema are strict.
- **The verdict log**: one row, `schema: "prose/verdict-none@1"`, `kind: "none"`, in the project's `verdicts.jsonl` and the per-user one (like a pick), carrying set, set uid, form, register, voices, `closest`, `reasons`, `note`, `shown`. It has no style vectors, no winner and no loser. `readVerdicts` returns it in a separate `none` array and **never** in `rows`; the taste model, the pick counters, `taste stats` and the duel counts read only `rows`, so none of them can count it (tested, including a log that mixes pick and none rows, and the server's tail read, which skips none lines so they cannot push pick rows out of its window of the last rows). An older log stays valid (it has no such rows); a runtime older than this one would count a none row as a malformed line, not as data. The row is appended once per (project, set, set uid, content): a retry after a crash adds nothing.
- **The set**: `set.json` gains `sentBack: { closest, reasons, note?, at, shown }`, written last (after the log rows and the reveal), so a retry after a crash finishes the job. `set show` prints `status` (`open`, `picked`, `sent back`) and `sentBack` (with the closest variant's direction); `set list` prints `status`.
- **Decision: a sent-back set is closed.** It takes no pick, no duel, no new prediction (model or agent) and no brief edit (E_CONFLICT, with the hint `prose set new --redo <id>`), it cannot be opened on the page, is not "pending", and cannot be a refine round. Reason: the owner judged it with those variants and that brief on screen and said none works; a later pick would contradict the recorded outcome and would have to be scored against a guess that was already revealed. The cost is one command (`set new --redo`).
- **`set new --redo <id>`** reuses `createSet` (one creation path): the draft argument becomes optional (it defaults to the draft the old set was made from; `--dir` finds the project), the brief is copied whole (confirmation included), the `original` is copied whole (so a draft that changed since shows as stale rather than silently pointing at other lines), `redoOf` and the owner's `feedback` are written, and the output prints `redoOf` and `feedback` (reasons as ids and as words, the closest variant with its direction, the note). It refuses a set that was not sent back (E_CONFLICT, with a hint that depends on whether it was picked or is still open) and cannot be combined with `--character`, `--context`, `--brief-from`, `--brief-confirmed` or `--lines`.
- **Sealed prediction**: sending back reveals the agent's guess like a pick does, but unscored: `reveal.json` (set and session) carries `outcome: "none"`, `picked: null`, the agent's pick, shortlist and why with `unscored: true` and no `hit` fields. **No row is written to the predictions ledger**, so the agent's accuracy (`taste stats`, hit rate) gains neither a hit nor a miss. The taste model's sealed guess is read and validated as at a pick (an edited or missing file still shows as such) and revealed the same way, with `unscored: true` and no hit fields; it is not counted either. A tampered agent seal is ignored (nothing is revealed, and the note says so); the sent-back outcome itself is still recorded. With no prediction the reveal says there was nothing to reveal. The guard test that only the reveal paths read the model prediction now lists two: a pick and a send-back.

### The reading session

- A new session event `none { closest, reasons, note?, eventId? }` (the candidate index that came closest, or null). It is accepted in the lineup, duel and refine stages (the page offers it only on the lineup), ends the session like a ship (stage `sentBack`; every later event is refused with 409), and is one of the events the page may send. The server runs `set none` for the **current round's set** first and appends only if that succeeded (so a set picked elsewhere meanwhile refuses with the CLI's message and writes no event), then writes the session's reveal. In a session with refine rounds the pinned champion of an earlier round belongs to another set, so the page does not offer it as "closest" and the server refuses it; the earlier rounds' sets are left as they are (open, unpicked).
- The reveal route serves once the session is shipped **or** sent back; the payload's `reveal` becomes `{ shipped, sentBack }`, `state.sentBack` carries what was said, and `session.lastFeedback` carries the redo note. Strikes are read-only after a send-back, as after a ship.

### Batch

- A batch item stages a send-back like a choice: `POST /api/queue/<id>/sendback { item, closest, reasons, note?, eventId }` (validated; refused for an item that is sent, sent back or closed, one that is no longer in the lineup, and a draft not in the set), logged as a queue event `sendback`. A later choice replaces it, a send-back replaces a staged choice, a skip or a cleared choice drops it. **Nothing is recorded until Send.**
- Rail status words: **Sent back, not sent yet** (staged) and **Sent back** (sent; "Sent back outside this page" when `set none` was run from the command line). The mark is a hollow circle with a short bar (filled once sent), distinct from the red slash of a skip, and always beside its words. The rail summary and the dock tally read "N of M chosen, K sent back"; the Send review is headed "Send 1 pick and 1 send-back?", states "N chosen, M sent back", lists one line per item (a send-back line is "where: sent back - reasons, note"), and warns that picks and send-backs cannot be changed once sent.
- Send applies, per item in rail order, either the existing lineup and ship pair or the session's `none` event (event id `<sendId>-<n>-n`; idempotent; a failure blocks only that item with the CLI's message). A sent-back item cannot be changed (choose, skip and sendback answer 409 "already sent back"); the item's own event route still refuses everything but `play` and `peek` (403), so a send-back can only go through Send. A set sent back from the command line while the queue is open shows as sent back, as a set picked there shows as picked.
- **Done**: every item resolved (sent or sent back) is `done`; a skipped or waiting item is never done by itself (a skip returns to the queue); Finish and `reading close` leave sent-back items as they are and only abandon what is left.

### The agent protocol

- **Single session**: `reading wait --id <session>` returns `event: "none"` with `outcome`, `set` (the round's set), `closest` (the variant number in that set), `closestLabel` (the letter the owner saw), `reasons`, `reasonWords`, `note`, `reveal` and a `next` that says to read the feedback, tell the owner what will change and run `set new --redo`. `reading status` shows `stage: "sentBack"`, `sentBack` and the reveal; `reading list` shows the stage; `reading close` leaves it.
- **Queue**: `reading wait --id <queue>` delivers sent-back items in a new `sentBack` array beside `picks` (each with `item`, `set`, `closest`, `closestLabel`, `reasons`, `reasonWords`, `note`, the unscored `reveal`, `via` and a `next`). The cursor counts picks and send-backs together, in the order they were recorded, so `--since` replay still works. `counts` gains `sentBack`; a staged send-back counts as waiting, like a staged choice (it is not an outcome, and its text is never in `status` or `wait`). The reason of `done` is `all-picked` when every item was picked (unchanged, with `sentBack: []`) and `all-resolved` when some were sent back. `reading status --id <queue>` shows `status: "sentBack"` with a `sentBack` object and the reveal for those items; `reading list` shows `sentBack` per queue. Sessions and queues without a send-back print what they printed before, plus the new empty or zero fields.
- **Skills**: `prose-review` and `prose-review-batch` each gain a short section: on a sent-back set read the feedback, do not repeat the rejected directions, say what you will change, then `set new --redo`.

### Deviations from the design as first decided

1. **The verdict row is its own schema, not a `kind` of `prose/verdict@2`.** A `kind: "none"` row under `verdict@2` would have to carry a winner, a loser and style vectors, and a taste reader that forgot to filter on `kind` would fit it. A separate schema id (`prose/verdict-none@1`) read into a separate array cannot be mistaken for a pick or a duel by any reader of `rows`. The price is that a runtime older than this one counts the line as malformed.
2. **No sealed-prediction requirement.** `set pick` refuses without a seal unless `--no-predict`; `set none` does not (a send-back has no pick to compare, so there is nothing to protect), and reveals nothing when there is no seal.
3. **Statuses in a batch**: the staged and the sent send-back are two statuses (`back`, `sentBack`) the way a staged and a sent pick are (`picked`, `sent`). The rail's word for a staged one is "Sent back, not sent yet".
4. **The panel is a modal dialog** (as asked), unlike the Send and Finish panels, which are non-modal regions; its keyboard handling is its own (Escape, a Tab trap) and the batch shortcuts are off while it is open.
5. **`reading wait` reports send-backs in a `sentBack` array**, not inside `picks`, so a caller that only reads `picks` never mistakes one for a pick.
6. **`set new --redo` copies `original` as snapshotted** rather than re-reading the refs from the current draft.

### Limits

- A refine round's pinned champion cannot be named as "closest". A send-back ends the session, so a multi-round session cannot send back and continue; open a new session for the redo set. The earlier rounds' sets stay open.
- The closest draft is shown to the agent (with its direction) but not to the owner on the redo set.
- Browser coverage is by hand (Chrome driven through Playwright at 1280 and 390 px, light and dark), not an automated suite: the repository has no browser test harness yet (the W2 plan names one). The pure page helpers and the page source are tested in `tests/none-page.test.ts`; the server and the agent protocol with the real CLI behind them in `tests/none-flow.test.ts`; the data layer in `tests/none-core.test.ts`.
